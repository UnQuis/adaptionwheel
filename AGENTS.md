# AGENTS.md

## What this repo is

- **Not a source repo for the Terraria mod.** The `3670588280/` folder mirrors the Steam Workshop item **ADAPTIONWHEEL** (Workshop ID `3670588280`): compiled `ADAPTIONWHEEL.tmod` builds under `3670588280/<tmodLoader-version>/`, plus `workshop.json` metadata. The C# source lives elsewhere.
- **Also the source repo for a Minecraft port**: a NeoForge 1.21.1 mod `adaptionwheel` (Adaption Wheel, Mahoraga from Jujutsu Kaisen) built from the decompiled Terraria mod for maximum fidelity. The Gradle project lives at the repo root.
- **It IS a git repo** (this line used to say otherwise): private `github.com/UnQuis/adaptionwheel`, default branch `main`. Other branches: `26.3` (newer Minecraft, usually checked out in a worktree) and `arena/*`. Pull before working.

## Layout

### Terraria artifacts (`3670588280/`)
- `3670588280/<tmodLoader-version>/ADAPTIONWHEEL.tmod` — compiled mod builds.
- Subdirectory names (`2025.12`, `2026.1`, `2026.2`) are **tModLoader versions**, not mod versions (match the `TMOD.*` header inside each `.tmod`).
- `workshop.json` — Steam Workshop metadata. Edit only when republishing.
- `3670588280/test/` — stale scratch Gradle project holding an **outdated copy** of the mod resources (missing newer assets). Ignore it; never edit it expecting changes to ship.

The distinction is load-bearing: a material listed under two tiers stays reachable from the lower one and trainable at the higher one, which is the only reason the Diamond tier can be raised at all (the whole deepslate family is stone-band, so `tierOf` calls all of it Stone). **The Diamond tier trains on the entire deepslate family** — deepslate and all its cut variants, infested deepslate, tuff, calcite, dripstone — because its original list (obsidian, ancient debris, netherite blocks, respawn anchors, lodestone) was ungrindable: ancient debris barely spawns. It also keeps `#minecraft:diamond_ores` and `#minecraft:emerald_ores`, which vanilla bands as *iron*-pickaxe blocks, so they train whichever tier you are on. **Luck:** each tier multiplies what ore drops and the experience it pays by 1/2/3/5/10 by tier (`FistTiers.luckMultiplier`, stated on the HUD row as `LUCK xN`). Implemented in `server/FistLuck.java` on `BlockDropsEvent`, which fires from `Block.playerDestroy -> Block.dropResources -> CommonHooks.handleBlockDrops` after the loot table has run but before anything enters the world, and carries the items and the XP in one object — so fortune and silk touch are already baked in before the multiplier applies, and drops and XP cannot drift apart. Stacks are merged up to their limit rather than spawning N entities. Scope is the `adaptionwheel:fist_luck` block tag, which ships as the eight vanilla `*_ores` tags plus `nether_quartz_ore` (there is **no** `minecraft:ores` tag in 1.21.1, and nether quartz ore has no tag of its own); stone, wood and wool are deliberately untouched so stone farming stays where vanilla left it. Config `mutations.fistMastery.luckEnabled`. Luck stays live during Adversity, unlike levelling — it is a property of how strong the fist currently is, in the same family as the harvest gate and the speed. Every unlock and tier-up prints which material trains it (`adaptionwheel.fist.material.*`) and how many blocks the next level costs. **Hook: `PlayerEvent.HarvestCheck` only — no mixin**, because that one check gates both the drops and the destroy-speed divisor. **Speed is tool parity, not a bonus**, and the prototype is chosen **per block** across the four vanilla tool classes (pickaxe/axe/shovel/hoe): soil and sand copy the shovel, logs the axe, foliage the hoe, stone and ore the pickaxe. All four classes of a tier declare the same number (wood 2, stone 4, iron 6, diamond 8, netherite 9 in 1.21.1), but asking the tool that can actually mine the block is what makes that true by construction. **Read the speed from the tool's own `Tool.Rule` list, never off a block and never off `defaultMiningSpeed`** — both of those read 1.0 and silently reduce the fist to bare-hand speed: `defaultMiningSpeed` is only the fallback for uncovered blocks, and `Item.getDestroySpeed(stack, block)` returns >1.0 only when a rule covers *that* block, so a diamond pickaxe reports 1.0 on dirt (1.21.1 keeps dirt in shovel-only `mineable/shovel`, out of `mineable/pickaxe` entirely) — which is exactly how a diamond fist ended up taking 15 ticks on soil where a diamond shovel takes 2. Tools are looked up by id through `BuiltInRegistries.ITEM` (the decompiled `Items` class is missing `copper_pickaxe` here); declared speeds are cached per (tier, class), and a missing tool makes the tier inherit the speed below. It is applied as a **multiplier** on the incoming `BreakSpeed` value, not an absolute overwrite: vanilla's pipeline is `1.0 × BLOCK_BREAK_SPEED × haste ÷ 5 airborne × submerged`, and multiplying swaps the 1.0 while keeping every modifier, whereas assigning an absolute value would ignore haste and remove the airborne penalty. **The client must answer too** — `MultiPlayerGameMode.continueDestroyBlock` accumulates break progress client-side and destroys the block itself, so a server-only hook makes the player mine at 1/3.3 of the intended speed. `FistMastery.onHarvestCheck` therefore runs on both sides (via `SurfaceAdaptations`), and the tier-reach rule lives in `FistTiers.reachTier` with **one** implementation called by both `FistMastery` and `ClientAdaption` — they previously drifted, leaving the client mining at wooden speed for a whole tier after the server had unlocked stone. **Harvest bands follow vanilla's own tool tiers**, sourced from the `needs_*_tool` block tags (cumulative reach): Wood = blocks needing no pickaxe; Stone `= #minecraft:needs_stone_tool` (+ coal, which vanilla leaves untiered); Iron `= needs_iron_tool`; Diamond `= needs_diamond_tool`. **There is no copper tier.** Vanilla's ladder has six materials, but copper owns no tool band — a copper pickaxe is a stone-band tool — and `copper_pickaxe` is absent from this registry entirely, so a literal six-tier ladder had a rung that granted nothing and cost a whole eight-level climb. It is folded into **Iron**, which now trains on the union of the Nether band (netherrack/basalt/blackstone/glowstone/magma/soul soil/crimson family — the only unclaimed material band) and everything `needs_iron_tool`. Saving progress: `WheelData.migrateLegacyConcepts` folds a carried `Fist_Copper` level into `Fist_Iron` on load, clamped to the cap, so a wheel played on the old layout keeps its investment. Netherite is what *no* pickaxe can harvest (dragon egg, spawner, reinforced deepslate); its level 8 is Instabreak. Material classes are data-driven block tags `data/adaptionwheel/tags/block/fist_{wood,stone,iron,diamond,netherite}.json`; a block in no tag is always harvestable (vanilla already allows it). Every unlock and tier-up prints which material trains it (`adaptionwheel.fist.material.*`) and how many blocks the next level costs. Config `mutations.fistMastery.fistSpeedScale` (default 1.0) multiplies the tool speed. **Instabreak** = Netherite 8: any breakable block in one tick, toggled with a keybind (default G, `client/AdaptionKeybinds.TOGGLE_INSTABREAK_KEY`) and validated server-side (`network/FistInstabreakPayload`); blocks with destroy speed -1 (bedrock, end portal) stay unbreakable. Runtime-only stance + block counter live in static maps cleared on logout/unequip/reset — they are deliberately NOT adaptation data, so they never reach the wheel item. HUD row shows `Material [Lv.n > n+1] : done/total blocks` and is pushed **immediately on each break** by `network/FistProgressPayload` (four bytes, `FistMastery.pushProgress`) — the 1 Hz full sync alone left a break invisible for up to a second, and the 1 Hz copy remains as the recovery path. The fist is frozen during Adversity like every other analysis. Config section `mutations.fistMastery` (also gated by `modules.mining`). 79 gametests across `test/`: `FistGameTests` (31), `CommandTreeSyncTests` (7), `WheelTierTests` (7), `SynergyTests` (5), `SheddingTests` (6), `DiscipleTests` (4), `DomainExchangeTests` (10), `AltarOfferingTests` (5), `TradeWheelDataTests` (4).   - **The altar's item→mob index now says what it loaded, and forgets itself when the world ends.** `AltarOfferings` is a lazily built static map, which is the worst kind: a data file naming an item this build lacks is skipped, a file that fails to parse is logged and skipped, and a mob with no file at all is simply absent — so "the altar opens and offers me nothing" is indistinguishable from "this item is not an offering" and from "my wheel already knows everything it opens". It therefore logs one INFO line on server start (`ServerStartedEvent` → `allMobs`, which also moves a directory walk out of the first player's first click), warns per item it could not resolve, and clears on `ServerStoppedEvent` — which its javadoc had claimed was happening for a long time and nothing actually called.
  - **The mapping is generated and shipped, not scraped at runtime**, and that is a decision rather than an accident. Reading "which mobs drop this item" out of the loot tables is the obvious implementation and it was rejected for three reasons: `LootPool`'s entry list is a `private final` field behind `LootPoolEntryContainer` on 1.21.1, so reaching the items needs an unwrap that differs between branches; the loot table *shape* changed on 26.3 (`functions` → `modifier`, `item` → `name`), so the same walk is two parsers; and a mob's loot is static data being re-derived 58 times. **Vanilla's 84 mob loot tables turned out to be byte-identical between 1.21.1 and 26.3** (`diff -rq`, no differences) — the shape change applies to tables *the mod authors*, not to vanilla's — so the data set is one set of files for both branches. A mod that changes its mobs' drops ships its own file.

The price of each level is the first level's price multiplied by `ritual.tradeCostGrowth` (2.0) once per level already held, and capped by `ritual.tradeMaxItems` (32) and `ritual.tradeMaxXp` (30) — so a level-based adaptation costs 1‑2–4–8‑16‑32‑32‑32 items and 1‑2‑4‑8‑16‑30‑30‑30 experience from empty to max, while a one-time `Env_`/`Move_`/`Debuff_` still has no levels to grow. **`DomainExchange.grow` applies the cap inside the loop**, because a growth factor and a cap otherwise multiply unchecked. A base of zero stays zero: the recipe price doubles as "the altar takes this item", and growth must never turn *not for sale* into *very expensive*.
  - **The prices are per row and synced, never recomputed on the client**: a level's price depends on how many levels the fed wheel holds, and the client has no fed wheel. `TradeSyncPayload` therefore carries one `(items, xp)` per candidate, plus a flag saying whether the altar takes the offering at all — because an empty list has two causes that want opposite answers ("wrong item" vs "your wheel already learned everything this item opens"), and only the server knows which.

Whole levels, not fractions — vanilla experience is an integer and part of a level has nowhere to live. Charging is `giveExperienceLevels(-price)`, the same call vanilla uses for an enchanting table, so the client's bar updates through the ordinary path. Experience is deliberately **not** synced: the client already has it, and a second copy would be a second source of truth.

## Gotchas that cost real time

- **Advancement `parent` must be namespaced.** `"parent": "root"` resolves to `minecraft:root`, and `AdvancementTree.tryInsert` returns false for a missing parent — which drops that advancement *and its entire subtree*, with one `ERROR Couldn't load advancements: [...]` line and no per-file reason. 33 of 34 failed this way. Advancement `title`/`description` are `Component`s, so a bare string is literal text: every name would have rendered as `adv.adaptionwheel.root.title`. Use `{"translate": "..."}`.
- **A criterion trigger cannot be registered with `CriteriaTriggers.register` in the mod constructor** — it writes straight into the frozen static registry and throws `Registry is already frozen`, taking the whole mod down. Use a `DeferredRegister` on `Registries.TRIGGER_TYPE`; note it also namespace-resolves, so a bare name lands as `minecraft:`.
- **`ItemPredicate`'s field is `items`, not `id`, in 1.21.1** (`{"items": "mod:thing"}` or a list). `display.icon` uses `id` because that is a *different* codec — an item stack — which is exactly why the two look interchangeable.
- **A stale `runs/gameTestServer/config/adaptionwheel-*.toml` can loop the config tracker forever** ("not correct. Correcting" repeated every tick, with `-1.toml.bak` … `-5.toml.bak` piling up), hanging the run with no exception. **Delete the config file first** whenever a gametest run hangs for no visible reason. A fresh file is generated cleanly.
- **A `while` loop over `getAdaptCount()` never terminates.** It is cached (`cachedAdaptCount`) and writing into `levels` directly does not invalidate the cache, so the condition never moves and the server thread freezes with nothing in the log. Call `invalidateAdaptCount()` after mutating, and bound such loops so a future mistake fails an assertion instead of deadlocking the run.
- **A test without a trailing `helper.succeed()` reports as "Didn't succeed or fail within 100 ticks", not as a failure.** Six tests written that way looked like a mysterious hang. Every test method must end in `succeed()`.
- **`minecraft:is_dark` does not exist as a biome tag in 1.21.1**, and a missing tag is only a WARN at load. The mod owns `adaptionwheel:dark` instead. The `neoforge:add_spawns` biome modifier codec also takes a **single** tag or id, not the list its javadoc promises.
- **`PathfinderMob` is in `net.minecraft.world.entity`,** not `net.minecraft.world.entity.monster`, in 1.21.1. `DeferredHolder<R, T extends R>` means the second type argument is the `EntityType` itself: `DeferredHolder<EntityType<?>, EntityType<DiscipleEntity>>`. The model layer event is the **nested** `EntityRenderersEvent.RegisterLayerDefinitions` — there is no top-level class of that name. `HumanoidModel.createMesh` returns a `MeshDefinition`; the event wants `LayerDefinition.create(mesh, 64, 64)`. `PlayerInteractEvent` exposes `getItemStack()`, not `getItemInHand()`, and `LivingChangeTargetEvent.getNewAboutToBeSetTarget()`, not `getNewTarget()`. Effect and attribute APIs take `Holder<MobEffect>` / `Holder<Attribute>`, so a `DeferredHolder` is passed directly rather than `.get()`. `getPlayers` is on `ServerLevel`, not `Level`.
- **Gametest batches hold 50.** A run whose suite spills past 50 into a second, incomplete batch did not terminate here; keeping the suite at 59 in one batch does. Worth remembering before adding another 40 tests.

## Gotchas

- `.tmod` files are **not** plain ZIPs: `TMOD.<version>` header + .NET length-prefixed version + hash + signature + 4-byte length + file table + raw-DEFLATE blobs (`zlib.decompress(blob, -15)`). Extract with `/tmp/opencode/tmod_extract.py`; decompile with `ilspycmd` (`.NET` tool) — the decompiled reference source lives at the repo root in `ADAPTIONWHEEL/` (incl. original `Assets/Sounds/*.wav`, textures, shaders, localization).
- `.rawimg` Terraria textures = XNB TiledImage: int32 tile count, then per tile (int32 w, int32 h, raw BGRA pixels). Convert with Python/PIL.
- Surface physics: ice/slime/cobweb are handled by **mixins** (`mixin/` package) so vanilla physics apply unchanged on both sides; lava swimming is tick-based velocity conversion in `ClientSurfaceHandler` (+ server mirror `AdaptionEvents.applySurfaceEffects`) because NeoForge 21.1 has no fluid-movement hook. Don't replace the mixin approach with post-tick velocity multipliers — that halved walk speed (the original bug).
- **Important:** `gradle.properties` is read by Gradle as ISO-8859-1 — keep `mod_description` and any `${...}`-expanded values in `neoforge.mods.toml` ASCII-only or the text will be mojibake'd.
- **NeoForge 21+ dependency format:** `[[dependencies.<modid>]]` uses the `type` field (`required|optional|incompatible|discouraged`); the legacy Forge `mandatory=true/false` key is silently IGNORED and every parsed dependency defaults to REQUIRED. The DE soft-compat entry once crashed every install without Draconic Evolution because of this.
- **The two screen hooks have INVERTED coordinate spaces, and that inversion is the whole porting hazard of both screens.** On 1.21.1 the slot-well loop lives in `renderBg`, called from `renderBackground` **before** vanilla pushes `translate(leftPos, topPos)`, so every coordinate there is absolute and the mouse needs no offsetting; adding `leftPos` on top of an already-translated frame draws the panel at double the offset, shoved into the bottom-right corner with the wells twice as far from the items as the items are from each other. On 26.3 the same hook is `extractLabels`, which runs **inside** the translate, so coordinates are relative and the mouse is offset by hand. `super` is called **last** on 26.3 because the title has to land on top of the panel.
- **1.21.1 hands the mouse over in GLFW's numbering, where the left button is 0.** That is the literal every other 1.21.1 screen asks for. 26.3 numbers it 1 (`MouseButtonEvent.button()`), and a "0 means left" test ported across unchanged **never fires**; on a container screen the click then falls through to `super`, which returns true unconditionally, so the game looks like it ate the click — which is exactly what silently killed both screens' rows and tabs. 1.21.1's `mouseDragged` also takes the button as its third argument (`double,double,int,double,double`).
- **The `BlockState` codec and the block set are both version-specific, and neither failure is a warning.** A jigsaw processor list written for 26.3 (`{"id":..., "properties":...}`, or a bare id string) fails the whole dynamic registry on 1.21.1, which wants `{"Name":..., "Properties":...}` and rejects a bare string — the message names neither the field nor the file. And the copper chain family arrived in 1.21.2, so a structure saved on 26.3 cannot ship as-is here: an unknown block in a template is a failed registry load. `tools/temple_variation.py` therefore takes `--game`, writes the shape and substitutes `iron_bars` for chains, and its `save_nbt` writes through a temporary file because the tool is often pointed at the checked-in template and `gzip.open(path, "wb")` truncates its input before writing a byte.
- NeoForge 21.1 API quirks hit during development: **`LivingIncomingDamageEvent` DOES exist** (this file used to claim the opposite) and it `implements ICancellableEvent`, fired from the very top of `LivingEntity.hurt()` via `CommonHooks.onEntityIncomingDamage` with `return false` on cancel. `LivingDamageEvent.Pre` fires later, inside `actuallyHurt()`. **Anything cancelled in the incoming handler can never be seen by the Pre handler** — reflection/compensation logic has to live in the incoming one (this is why the existence reflection used to be dead code). `DamageSource.type()` returns `DamageType` (use `typeHolder().getRegisteredName()` for the id); `AttributeModifier(ResourceLocation, double, Operation)` with `Operation.ADD_VALUE/ADD_MULTIPLIED_BASE`; `AttributeInstance.removeModifier(ResourceLocation)`; `MobEffectEvent.Applicable.Result.DO_NOT_APPLY`; `PlayerTickEvent` lives in `net.neoforged.neoforge.event.tick`; `StreamCodec.composite` supports at most 6 components (use `StreamCodec.of` for more); `Mob` has no `isBoss()` — boss detection lives in `BossHelper` (hardcoded Wither/EnderDragon/Warden + Chaos Guardian + boss tag); loot params in 1.21.1 use `ATTACKING_ENTITY`/`DIRECT_ATTACKING_ENTITY`/`LAST_DAMAGE_PLAYER` (renamed from `KILLER_ENTITY`/`DIRECT_KILLER_ENTITY`/`LOOTING_ENTITY`); `LootParams.Builder` takes a `ServerLevel`; `FoodData` has no `getMaxFoodLevel()` — max food is the constant 20.
- **The block-drop gate is `PlayerEvent.HarvestCheck`, NOT `Player.hasCorrectToolForDrops`.** NeoForge's patch swapped the latter for `BlockState.canHarvestBlock(...)` → `EventHooks.doPlayerHarvestCheck(...)`, which posts the overridable `HarvestCheck` event. The *same* check also picks the destroy-speed divisor (`/30` with a correct tool vs `/100` without) inside `BlockBehaviour.getDestroyProgress`, so a single `setCanHarvest(true)` grants both the drops and the correct-tool speed bonus — no mixin required. Confirm in `~/.gradle/.../neoforged/neoforge/<ver>/…-userdev.jar` → `patches/net/minecraft/server/level/ServerPlayerGameMode.java.patch`.
- **Curios**: `ICuriosItemHandler.isEquipped(Item)` is a default method delegating to `findFirstCurio(Item).isPresent()`. Therefore whenever `wearingWheel(player) == false`, `getWheelStack(player)` is **guaranteed empty** — writing to the wheel from a `!wearing` branch is a guaranteed no-op. Use `PlayerAdaption.equippedStack` (captured while worn) for those writes.
- **1.21.1 gametests**: templates live at `data/<ns>/structure/<path>.nbt` — **singular** `structure` (not `structures/`) and **gzipped binary NBT** (SNBT text is only read from the IDE test-structures dir). NeoForge prefixes the template with the lowercased test class name unless `@PrefixGameTestTemplate(false)` is set. Any test calling `GameTestHelper.makeMockServerPlayerInLevel()` is **broken while Curios is installed**: the mock login makes Curios throw `Payload curios:sync_data may not be sent to the client!`, failing the test before its body runs. `./gradlew runGameTestServer` is the headless runner (`forge.enabledGameTestNamespaces` is already wired in `build.gradle`).
- Mixin quirks hit with the DE laser mixin: an `@Redirect` handler parameter must match the **exact** receiver type in the target bytecode (`Player`, not `LivingEntity` — supertypes are rejected at apply time with `InvalidInjectionException`); `@At(target = "setHealth(F)V")` without an owner matches any receiver, which keeps the injection resilient; optional mixins into another mod's classes must be gated through an `IMixinConfigPlugin` (`shouldApplyMixin` → `FMLLoader.getLoadingModList().getModFileById(...)`) or Mixin logs errors for the missing target class.
- Draconic Evolution facts (from the jar at the repo root): the Chaos Guardian (`draconicevolution:draconic_guardian`) is NOT in any boss tag — recognition is hardcoded via string id; its parts are NeoForge `PartEntity`s, so generic part unwrapping covers them; ALL guardian damage types bypass armor/resistance/effects/shields/cooldowns and most are tagged `is_explosion`/`is_projectile` (so vanilla-tag categories already partially apply); the charged twin laser writes health directly (handled by mixin).
